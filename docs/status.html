Five capabilities, checked against the tree. The recurring finding is not that things are unbuilt — most of them are built well. It is that they are built somewhere else, and the framework has not yet taken them into a vocabulary an application can reach without going hunting.

Dimension 01 · Rendering

General-purpose SDF pipeline

Mature in the engine · absent here

The pixels path is real end to end and has been pressure-tested by a design tool: Surface → SurfaceCompiler → SdfScene → SdfComposer → SPIR-V → SampledColorTarget → Node.image. What is missing is a compositing vocabulary and any framework-level presence at all — three mentions of SDF across the four modules, all of them Javadoc prose.

Surface tree → SPIR-V, with symbolic AD and a structural shader cache In the stack
Runtime parameters without a recompile — push constants, then the buffer road In the stack
N techniques in one pass, interleaved per pixel by shared depth In the stack
GUI viewport compositing — marched target sampled as a laid-out node In the stack
One composition root — today the engine and GuiApp are two Specified
Layer & blend vocabulary — order and depth are the only composition Absent
A rasterising technique — ClipDepth still has one author, one consumer Absent
Framework SDF vocabulary — no viewport component, no scene provider Absent

Standing on its own

  • Complete modelling vocabulary — primitives, domain ops, all three smooth booleans, Implicit with forward-mode symbolic AD.
  • ShaderCache keyed on structural equality of the whole SdfScene: records all the way down, so caching needed no bespoke fingerprinting.
  • ConeField reads geometry from a storage buffer — one pipeline for every scene, after a few hundred segments were measured at 5 s of pipeline build on the frame loop.
  • The designer's three B0 stages — parameters, function-abstracted lowering, node identity — are all done.

What an app still retypes

  • The two kinds of dirty: a scene change is new SPIR-V and a new pipeline; a frame change is six floats of push constant.
  • The queue discipline: VkQueue is not thread-safe, so a drag handler raises a flag and all GPU work happens in one pump() in FrameStage.APP.
  • Every SDF app writes both by hand. That is the same drift the framework was created to absorb, one layer down.
  • Designer stages P3–P8 open: cost walk, off-thread compile, resolution swap, edit vocabulary, serialisation, pick pass.
Dimension 02 · Concurrency

Multithreaded by default

Designed in full · zero code

The detailed plan exists — one component, one thread, one mailbox, with the mapping decided in the wiring and never at runtime. One line of it is now built: the container owns the application's bus, so there is one fabric to place a component on. Everything about placing one is still unwritten. A grep of all four modules' main sources returns zero occurrences of Thread, Executor, java.util.concurrent, volatile, synchronized or Atomic. The entire thread-aware API surface is one Runnable: WakeSource.onWake.

The model itself — static placement, platform threads, the Rate round trip Specified
Mailbox substrate — Pump, State, Fold, Backpressure In the stack
Cross-process actors — elektro-Q: Actor, Conduit, four transports In the stack
Timeline bridge — KronBridge folds a topic into a cell on the baton In the stack
The deadline half — Kron.sleepTimeout() already registered In the framework
The container owns the application's bus — one fabric, dialogs included In the framework
…and the thread its handlers run on — every Gui still makes a pool Absent
A WakeSource per component mailbox Absent
@MainThread actually enforced — inert until the processor Absent
Survivable component failure — supervision, per-grouping Overrun Absent

Settled, with reasons

  • Platform threads, not virtual — Kronometer's kernel recommends a single-carrier scheduler, so components on virtual threads would be the documented deadlock, not merely slower.
  • A component thread never touches the timeline. Work arrives Rate → mailbox → component thread → Topic → Cell, and the one drain period of latency is priced in advance rather than discovered.
  • FrameStage vs Rate settled: the frame is the main thread's recipe and its order is causal; a Rate is everyone else's grid.

Open before the processor

  • One bus is not one thread. The fabric is now the application's — the framework's tree and the dialogs share it — but Gui builds a cached pool in a field initializer and work() submits to that, so handing it an executor redirects handlers and leaves the pool. Closing that is an upstream change.
  • The dream case — responsive through a component's infinite loop — is not designed yet. Backpressure.FAIL is the default and resolves through Fatal, so a full mailbox kills the process rather than degrading.
  • Three vocabulary mismatches are recorded for the processor's brief: @Component is a DI contract not an actor one, @MainThread is two-coloured, FrameHooks is the barrier's N=1 case.
Dimension 03 · Ergonomics

One language, not five

Solved at the shell · open at the fabric

The app edge now has one language and the measurement is real: three ported wirings run 186 / 296 / 556 lines against a ~350-line scaffold that each application used to carry for itself, and two of the three import four or fewer sibling types. The app fabric still has four — Shell.krono() hands over a clock and then you are in Kronometer's language, and there is no Shell.bus() at all.

Gotchas already closed

  • The central contract stops being satisfiable by a lambda — as an interface, run(() -> myAppInfo, args) compiled and produced a blank window that refused nothing.
  • Shell's accessors refuse to hand over what does not exist yet, so work in the wrong phase is a throw rather than a null.
  • One Settings per application, which was the singleton invariant two repos maintained by a comment.
  • Launch.FRAMEWORK_KEYS means --automation is asked for the same way on every application on the desk.

Gotchas still open

  • Two reserved keys nothing consumes. --profile parses and no module honours it; the honest fix is @ConditionalOnType, which needs the processor.
  • shell.wake(gui::onWork) is redundant — GuiApp already wires every tree it presents — and reads like the line that makes the wake happen.
  • A non-default zoom range would disagree across the editor's three windows, because two of them also run under a host with no Shell to ask.
Dimension 04 · The thesis

The Boot analogue

Container real · the three multipliers unbuilt

The no-reflection thesis holds and three applications run on it. What is missing is precisely what makes Boot Boot: the generator that turns vocabulary into enforcement, the starter that makes one dependency enough, and the instrument that answers "why did we miss a frame".

Compile-time container, hand-wired — phases, launch, pacing, disposal In the framework
The driving socket — automation, off unless asked for In the framework
The annotation processor — nine annotations wait on it for enforcement Specified
-diagnostics, the Actuator analogue — blocked on a name Specified
@Subscribe — actor substrate, extension API and reactive automation, at once Specified
Starters and a BOM — four modules today, none of them a starter Absent
Aggregated reachability metadata — "probably the highest-leverage feature not yet listed" Absent
Simulation vocabulary — fixed step, scene, assets; the game-engine half Absent

Holding

  • Nothing reflects. Retention is CLASS deliberately; no Class.forName on the startup path.
  • -api and -core stay JDK-only, so every decision the container makes is testable with no GPU — which is why 80 tests run anywhere.
  • The spreadsheet half is demonstrated three times over: one window, three windows, and two windows on one device.

Not yet true

  • "A compile error beats a startup error" is the house rule and it is not in force — with no processor, @Component, @MainThread and @Setting are vocabulary without enforcement.
  • The game-engine half exists in the engine — render == sim, one IR to SPIR-V and to a CPU AST — and nowhere in the framework. FrameStage.APP is an empty slot, by design.
  • -diagnostics may be mostly free: atchung-probe already has spans, counters and stall-hunting, and Automation already imports it.
Dimension 05 · Verification

Driving the real application

Mature · three verbs from complete

The strongest area on this page, and the only capability where the framework's share is already finished. A running desktop application — real window, real Vulkan device, real frame loop — is driven over a loopback line protocol: one command in, one reply out, terminated by a lone ., replies beginning ok or err so a script branches on two characters. Sixteen verbs, a real cursor behind them, and a CLI whose exit status is the verdict.

The socket, wired once — --automation=7654 parses in every application In the framework
The verb set — find, click, drag, type, go, settle, await, shot In the stack
Pointer fidelity — a stateful cursor stepped at 125 Hz and paced in real time In the stack
Semantic read-model — roles, names and structure, joined to layout by id and frame In the stack
A client that is not a test fixture — ottermate, empty dependency block In the stack
A settle that consults the clock — today it photographs mid-fade and says ok Specified
zoom and resize — the last two things per-app --capture can do and this cannot Specified
A second socket per application — the designer places its own at port() + 1 Specified
The reactive half — a macro can drive the application but cannot react to it Absent

Why it is trustworthy

  • One input path, not a second one. The driver moves the same cursor a hand does, so a gesture that works here is a gesture that works — no synthesised event delivered to a coordinate.
  • Reveal or refuse. A click on a row a hundred-thousand-row table has scrolled past used to hit the header drawn over it, sort the table, and answer ok. Now the layout model publishes what is actually on screen and the target is revealed or the command is refused.
  • A busy port never stops a launch. Driver.open reports the drop by name and the application runs undriven — one of the six dropped-capability reports.
  • Proven against a planted defect: a hover-path bug diagnosed from the CSV alone, and recorded as necessary rather than sufficient.

What is left

  • A live defect, and the one thing to fix first. settle gates on gui.frameOwed() and never asks the Kron clock, so an application mid-fade returns ok immediately — click → settle → shot has photographed a panel three seconds before its transition finished. Automation holds a Gui and not a KronoGui, so the fix is new API rather than a change inside the verb.
  • Until zoom, resize and that settle land, per-application --capture cannot be retired and every app keeps its own headless entry point.
  • Automation is command-in, response-out. The @Subscribe seam is what would let a macro wait on something the application says.

The critical path

Ordered because the order is load-bearing, not for presentation: each step decides a vocabulary the next one bakes in.

01

Hand the container a bus landed

Shell.bus(), built in the constructor and available in every phase; the framework's Gui and the dialogs are both on it, so an application is one fabric rather than one per tree. The half that could not be added later without moving everything built on top of it. What is left of this step is the handler executor, which needs Gui's worker pool to stop being a field initializer — an upstream change, not another argument.

02

Make one application mean one set of threads

Gui(Atchung, Executor) exists but redirects only input handlers; Gui.work() still submits to a pool each Gui makes for itself. Owning the executor is what makes placement a decision in the wiring rather than a consequence of how many trees an application happens to hold.

03

Decide what a wedged component does

Supervision, mailbox overflow policy, and per-grouping Overrun. Today Backpressure.FAIL resolves through Fatal, so the default answer to a slow component is killing the process. This is the one part of the stated goal — responsive through an infinite loop — that the written model does not yet cover.

04

Write the processor

Reproduce the three hand-written wirings, then make @MainThread and the component colouring real. Deliberately last, and correctly so. It freezes what @Component means, which is why the concurrency model had to be settled first.

05

Starters, a BOM, and the stack's reachability metadata

One dependency that brings the whole stack, including hints an application inherits rather than assembles. The single highest-leverage item on the open-questions list, and the thing that makes the Boot comparison land for someone who has not read the docs.

06

Name and build the diagnostics module

Blocked on a name — vexelray-diagnostics is taken upstream for a different concept. Most of the substance may already be atchung-probe. Under the concurrency model "why did we miss a frame" becomes "which component's mailbox", and a probe already threaded through the bus is what answers it.
